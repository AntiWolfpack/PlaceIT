3. MARKETPLACE PAYMENT SECURITY
==================================================

PlaceIT is a multi-kitchen marketplace.

CRITICAL BUSINESS RULE:

ONE ORDER = ONE KITCHEN = ONE PAYMENT RELATIONSHIP

An order must belong to exactly one kitchen/vendor.

An order must NEVER contain menu items from multiple kitchens.

The server must enforce this.

Example:

Customer purchases from Kitchen A.

The order must contain:

vendor_id = Kitchen A

All OrderItems must belong to Kitchen A.

The customer must not be able to manipulate the request and change vendor_id after checkout.

If the customer wants food from Kitchen B, they must create a separate order.

--------------------------------------------------
PAYFAST
--------------------------------------------------

PlaceIT uses Payfast.

The intended marketplace architecture is:

Customer
    ↓
PlaceIT checkout
    ↓
Payfast
    ↓
Split payment
    ├── Kitchen/vendor's share
    └── PlaceIT commission

The current implementation should prepare for Payfast Split Payments but MUST NOT fake or simulate settlement.

Do not invent Payfast API behavior.

Do not assume that adding a vendor's Merchant ID automatically causes settlement.

Use Payfast's documented integration mechanisms.

The payment architecture must support:

- PlaceIT primary merchant account
- individual vendor/kitchen Payfast merchant accounts
- vendor-specific Payfast Merchant IDs
- PlaceIT commission
- vendor settlement
- payment status
- webhook/ITN verification
- idempotency
- refunds where supported
- payment audit records

Every vendor must eventually have a verified Payfast Merchant ID before that vendor is permitted to accept online marketplace orders.

Do NOT allow the frontend to supply or override the destination Payfast Merchant ID.

The backend must derive the vendor from:

Order → Kitchen/Vendor → verified Payfast Merchant ID

Never:

Request → client-supplied Payfast Merchant ID

--------------------------------------------------
PAYMENT INTEGRITY
--------------------------------------------------

The server must calculate:

- item price
- item subtotal
- order subtotal
- commission
- vendor amount
- payment amount

Use integer cents for money calculations.

Do not use floating-point arithmetic for monetary values.

Example:

R100.00 = 10000 cents

15% commission:

10000 × 0.15 = 1500 cents

Vendor amount:

8500 cents

All calculations must happen server-side.

The client may display calculated values, but the server is authoritative.

A malicious customer must not be able to modify:

- price
- commission
- vendor amount
- order total
- payment amount
- vendor ID
- payment status

by editing browser requests, localStorage, JavaScript, or API payloads.

6. AWS COGNITO AUTHENTICATION
==================================================

AWS Cognito is the authentication provider.

Do NOT create a second custom password-authentication system.

Do NOT store user passwords in PostgreSQL.

Passwords must never be stored in plaintext.

Use Cognito's secure authentication mechanisms.

Require email verification where appropriate.

Use secure token/session handling.

Access tokens must be short-lived where practical.

Refresh tokens must be handled securely.

Never expose authentication tokens through URLs.

Do not store sensitive authentication material in insecure localStorage.

Review the existing localStorage implementation carefully.

The customer's cart and receipt ID list may remain client-side if appropriate, but:

- they must not be treated as trusted data
- receipt IDs must be validated server-side
- cart contents must be revalidated server-side before checkout
- prices must always be retrieved from the database
- ownership must always be verified server-side

7. AUTHORIZATION / RBAC
==================================================

Implement/enforce:

CUSTOMER
VENDOR/KITCHEN
ADMIN

Server-side authorization is mandatory.

Customer:
- access own profile
- access own orders
- access own receipts
- cannot access another customer's order

Vendor:
- access only their own kitchen
- access only their own menu
- access only orders belonging to their kitchen
- cannot access another vendor's orders
- cannot modify another vendor's menu

Admin:
- authorized platform-wide access

Never trust a role value sent by the frontend.

8. DATABASE SECURITY
==================================================

Use PostgreSQL + Drizzle ORM.

Use Drizzle's parameterized query mechanisms.

NEVER build SQL using string concatenation with user-controlled values.

Avoid unsafe raw SQL.

If raw SQL is absolutely necessary, use parameterized/bound parameters.

Database credentials must remain server-side.

DATABASE_URL must never reach the frontend.

Production database must not be publicly exposed unnecessarily.

Use least-privilege database credentials.

==================================================
9. ROW-LEVEL DATA ISOLATION
==================================================

Implement BOTH:

A. application/server-side authorization
B. database-level Row-Level Security where technically appropriate

Do not assume PostgreSQL RLS alone replaces application authorization.

Do not assume application authorization alone is sufficient where RLS can provide defense in depth.

For every sensitive query, ensure the query is scoped appropriately.

Examples:

Customer orders:

WHERE order.customer_id = authenticatedUserId

Vendor orders:

WHERE order.vendor_id = authenticatedVendorId

Vendor menu:

WHERE menu_item.vendor_id = authenticatedVendorId

Never use only:

WHERE id = requestedId

without also checking ownership.

Protect against IDOR/BOLA vulnerabilities.

Example attack that must fail:

Customer A requests:

GET /api/orders/customer-B-order-id

The server must return an authorization failure or safe not-found response.

13. WEBHOOK SECURITY
==================================================

This is CRITICAL.

Payfast payment notifications/webhooks/ITNs must NEVER be trusted merely because they reached the API endpoint.

The backend must verify the notification using Payfast's documented verification/security mechanism.

Only after successful verification may PlaceIT:

- mark payment successful
- mark order paid
- create/confirm an order
- record commission
- update vendor payment state

Do not allow:

POST /webhook

with arbitrary JSON

to mark an order as paid.

Implement idempotency.

If Payfast sends the same notification twice:

- do not create duplicate orders
- do not create duplicate commission records
- do not double-credit a vendor
- do not double-process the payment

Store an appropriate unique payment/transaction identifier.
